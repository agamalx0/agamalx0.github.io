Splunk Knowledge Objects & Data Normalization

Milestone 2 of my Splunk SOC Engineering Series: standardizing selected fields, enriching events with asset context, simplifying searches, and grouping events into analyst-friendly categories.

By Ashraf GamalUpdated 17 November 2026Milestone 2 · Splunk SOC Engineering SeriesApprox. 9 min read
In this guide 1. Milestone scope and lab context 2. CIM field normalization 3. Asset and identity enrichment 4. Search optimization with macros 5. Event types and tags 6. Validation summary and limitations 7. Next: detection engineering
Milestone 2 completed

Milestone 1 established the collection pipeline. In this phase, I added a knowledge layer on top of the ingested data: CIM-oriented field aliases, an asset inventory lookup, reusable search macros, and event types with tags. The goal was to make searches more consistent and give analysts useful context without repeatedly rebuilding the same SPL.

1. Milestone scope and lab context

This work was completed in a single-node Splunk Enterprise lab. The available telemetry included Windows Sysmon, Kali Linux, and FortiGate firewall events. The Milestone 2 implementation notes focus on FortiGate traffic and Windows Sysmon when defining the knowledge objects; they do not document a Linux-specific lookup, macro, or event type.

The Splunk product version and add-on versions were not recorded in the milestone notes. For this public example, private lab addresses have been replaced with documentation-only addresses from 192.0.2.0/24. The original asset roles and relationships are preserved, but the example IP values are not the live lab addresses.

2. CIM field normalization with field aliases

The Fortinet add-on exposed source and destination IP values as srcip and dstip. The Milestone 2 implementation aligned those names with the shorter source and destination fields used by the searches:

Field aliasDestination field
srcipsrc
dstipdest

I created the field alias in Settings → Fields → Field Aliases → New with these values:

  • Name: fortigate_cim_alias
  • Apply to sourcetype: fortigate_traffic
  • Destination app: Search
  • Field aliases: srcip → src and dstip → dest
  • Overwrite field values: checked

Field aliases are configured as Splunk knowledge objects in Splunk Web; there is no SPL command that creates this alias. The object configuration is shown below. The next search verifies that the aliased fields are available at search time.

I ran the following validation search; the screenshot shows its 24-hour results:

index=network sourcetype=fortigate_traffic earliest=-24h
| table _time, src, dest, action, protocol
| head 10

Validation results: The Milestone 2 summary records 32,399 FortiGate events for this normalization step. The screenshot captures a separate 24-hour run with 32,388 events.

This is a targeted normalization step for two FortiGate fields. It demonstrates field aliasing, but it should not be described as full CIM validation or complete CIM data-model mapping across every source.

3. Asset and identity enrichment with a lookup

An IP address by itself does not tell an analyst whether the system is a domain controller, workstation, test host, or perimeter device. I created a small CSV inventory and made it available to Splunk searches through a lookup definition.

3.1 Build the asset inventory

The source CSV used these columns: ip, hostname, asset_role, and priority. The values below use documentation-only IPs in place of the private lab addresses:

ip,hostname,asset_role,priority
192.0.2.10,Splunk-Backend,SIEM,Critical
192.0.2.90,AD-Server,Domain Controller,Critical
192.0.2.35,Win-Endpoint,Workstation,Medium
192.0.2.36,Kali-SOC,Offensive/Test,Low
192.0.2.31,FortiGate-FW,Perimeter Firewall,Critical

I uploaded lab_assets.csv through Settings → Lookups → Lookup table files, then created a file-based lookup definition:

  • Lookup definition: asset_inventory
  • Lookup file: lab_assets.csv
  • Destination app: Search
  • Sharing: This app only for both the lookup definition and the CSV file

The lookup file and its definition are created and permissioned through Splunk Web. There is no SPL command in the milestone notes for creating or sharing the lookup object; the screenshot below records that configuration.

3.2 Enrich FortiGate events

The lookup matches the event's srcip to the CSV's ip column. I used this search to return the normalized and original source fields, destination, asset context, and action:

index=network sourcetype=fortigate_traffic earliest=-24h
| lookup asset_inventory ip AS srcip
    OUTPUT hostname, asset_role, priority
| table _time, src, srcip, dest, hostname, asset_role, priority, action
| head 10

The screenshot below shows the search results:

Validation results: The Milestone 2 summary reports 32,399 enriched FortiGate events and a 100% enrichment rate. The screenshot captures a separate 24-hour search run with 32,382 events. The notes give 192.168.100.31 as an example source address mapped to the FortiGate firewall asset, classified as a perimeter firewall with Critical priority. That address is represented by 192.0.2.31 in the public CSV example above.

The reported rate applies to the event set summarized in the implementation notes; it is not a guarantee that future events, new IPs, or other indexes will all match the inventory. The lookup in this milestone was applied to FortiGate source addresses.

4. Search optimization with macros

Repeatedly typing index and sourcetype filters makes searches longer and creates room for inconsistent spelling. I created two base search macros so the source constraints could be maintained centrally.

MacroDefinitionPurpose
sysmon_dataindex=wineventlog sourcetype=XmlWinEventLogWindows Sysmon searches
firewall_trafficindex=network sourcetype=fortigate_trafficFortiGate traffic searches

Both were created under Settings → Advanced Search → Search macros. Macro definitions are maintained in Splunk's knowledge-object settings; the strings in the table are the base search definitions, not standalone SPL commands to create the macros.

The documented Sysmon usage example was:

`sysmon_data`
| stats count by EventCode
| head 10

Validation results: The screenshot shows 15,453 Sysmon events for its 24-hour run. The Milestone 2 summary separately records 15,496 Sysmon events and 33,419 FortiGate events; these are recorded as separate run totals. A separate firewall macro query and its time range were not included in the detailed activity notes.

Centralizing the base searches means an index or sourcetype change can be handled in the macro definition rather than by editing every saved search. The macros in this milestone cover Sysmon and FortiGate; a Kali/Linux macro was not recorded.

5. Event types and tags

The final activity grouped events by function rather than only by the system that generated them. The milestone notes record two event types:

Event typeSearch stringTags
Network_Trafficsourcetype=fortigate_trafficnetwork, communicate
Windows_Privilege_Usesourcetype=XmlWinEventLog EventCode=4624authentication

The definitions were created through Settings → Event types → New Event Type. Event types are configured in Splunk Web; the source notes do not provide an SPL command that creates these objects.

Tags are assigned to the event types through their Splunk Web configuration. The tag assignments recorded in this milestone are shown below; the source notes do not include a separate SPL query validating tag-based retrieval.

Configuration caveat: I named this event type Windows_Privilege_Use, but EventCode=4624 represents a successful logon. That is authentication, not privilege use, so Windows_Authentication would describe the filter more accurately. The authentication tag is consistent with the event; I should rename the object or use a privilege-use event before labeling it as privilege use.

I used the Network_Traffic event type to group FortiGate events by action. The screenshot captures the last 24 hours:

eventtype=Network_Traffic | stats count by action

Screenshot result: The 24-hour search returned 32,870 events: 19,667 allowed, 13,197 blocked, and 6 teardown. The milestone summary separately reports 177,942 FortiGate events over seven days, including more than 100,000 allowed and more than 77,000 blocked events.

The screenshots and milestone notes capture separate searches and time windows. The summary table labels each count by its source and window; do not add these values together as a unique-event total or treat them as directly comparable measurements.

The source notes also state a potential 40–60% reduction in analyst triage time as an operational benefit. They do not include a before-and-after timing study or other measurement supporting that percentage. I therefore do not present it as a measured outcome of this lab.

Other boundaries of the documented work:

  • The field alias covers two FortiGate fields; full CIM data-model validation is not recorded.
  • The asset lookup enriches the FortiGate search using the source IP; no Windows or Linux lookup was documented.
  • The two macros cover Sysmon and FortiGate; no Linux macro was documented.
  • The event-type notes do not show a Linux authentication event type or a verified cross-source tag=authentication search.
  • Splunk and add-on versions, exact macro time windows, and a full set of raw sample events were not included in the milestone summary.

No external vendor documentation links were recorded in the source implementation notes. This article is a practical record of the lab work and the evidence summarized for this milestone.
