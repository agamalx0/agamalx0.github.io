IBM QRadar migration guide:
same or new IP address

A practical, version-aware walkthrough for replacing a QRadar Console appliance, preserving configuration and certificates, transferring Ariel data, and validating the new Console—whether it retains the existing IP address or moves to a new one.

By Ashraf GamalUpdated 11 October 2026Version-aware migration guideApprox. 12 min read
On this page1. Scope and decision2. Pre-migration checklist3. Same IP migration4. New IP migration5. Data transfer notes6. Validation and rollbackOfficial references
Important: this is a planned Console replacement workflow for non-HA deployments.

Do not use these steps as a substitute for a supported HA migration, disaster-recovery procedure, managed-host migration, or upgrade. Confirm the procedure for the exact QRadar version and appliance type before making changes. A migration can interrupt Console administration, event/flow visibility, and integrations. Schedule a maintenance window and establish a tested rollback plan.

1. Choose the correct migration path

IBM provides separate procedures for replacing a Console while keeping the existing IP address and replacing one with a new IP address. Both flows assume the managed hosts remain in the deployment and that the new Console is installed at a matching QRadar software version/fix level before the configuration is restored.

ScenarioWhat changesPrimary network consideration
Same IP addressThe new Console takes over the old Console's management IP.Move the old appliance to a temporary unused/decommissioned address first; only then assign the original IP to the new Console.
New IP addressThe replacement Console retains a different management IP.Update DNS, routing, firewall allowlists, source integrations, API clients, and monitoring that refer to the old address or hostname.

These procedures do not automatically migrate all QRadar app data, custom integrations, third-party application state, or every external dependency. Plan app data backup/restore separately, and inventory custom certificates, SSH keys, license state, WinCollect compatibility, managed hosts, and connections to external systems.

2. Pre-migration checklist

  • Record the old Console's appliance type, version, fix pack/patch level, hostname, IP/subnet, gateway, DNS, management interface, license details, and connected managed hosts.
  • On the old and new systems, confirm the QRadar software version with /opt/qradar/bin/myver. Match the version and fix level before restoring a configuration backup; the backup must be restored to a compatible matching QRadar version.
  • Install and configure the new appliance with a temporary or planned IP address, as appropriate for the chosen path. Do not put the same IP on both appliances at once.
  • Run an On Demand Backup from Admin → Backup and Recovery → On Demand Backup. Wait for completion, download the backup, and store a second protected copy outside both appliances.
  • Back up app data separately according to the specific app/extension's supported backup method. QRadar configuration backup/restore does not by itself guarantee app data is backed up or restored.
  • Document custom certificates and trust stores, custom-generated key pairs, /etc/ssh and /root/.ssh material where required, DNS records, integrations, API consumers, and any local Event Collector data in /store/ec.
  • Confirm sufficient capacity and storage on the destination; estimate Ariel data transfer duration and validate connectivity between the old and new appliances over SSH.
  • Have console/OOB access (such as IMM or a local keyboard) available for network changes. Confirm change approval, communication plan, rollback IP/network details, and migration acceptance criteria.
Version compatibility is not optional.

Use /opt/qradar/bin/myver on both appliances. If versions differ, do not assume the backup will restore cleanly. Follow IBM's version-specific install/patch guidance and create a fresh backup after any planned software change that affects the source deployment.

3. Migrating to a new Console with the same IP address

Step 1 — Prepare the replacement Console

  1. Install the new Console using the same supported QRadar version and fix level as production. Give it a temporary IP address and verify basic connectivity.
  2. Check the software version:
/opt/qradar/bin/myver

If WinCollect is in use, confirm the WinCollect version on the new Console matches the old Console before migration. Keep the old appliance available until the migration is accepted.

Step 2 — Back up the old Console and stop its Console services

Create and download an On Demand Backup, then preserve the backup file securely. During the approved cutover, stop the services listed in IBM's same-IP replacement procedure on the old Console:

systemctl stop hostcontext
systemctl stop tomcat
systemctl stop hostservices
systemctl stop tunnel_manager

These are service-impacting commands. Confirm the exact sequence in the documentation for the installed QRadar release and do not run them on the destination Console by mistake.

Step 3 — Move the old Console to a temporary address

Identify the management interface and its NetworkManager connection profile:

cat /etc/management_interface
cat /etc/management_interface_cp

Use the documented network-change procedure for your release. IBM's current same-IP guide demonstrates using the connection-profile UUID with nmcli to move the old appliance to an unused/decommissioned IP and update any required gateway/DNS values. Verify the new settings before applying them.

# Illustrative IPv4 pattern only — replace every placeholder
# with values confirmed for this host and release.
nmcli connection modify <UUID> ipv4.addresses <temporary_ip>/<prefix>
nmcli connection modify <UUID> ipv4.gateway <gateway_ip>
nmcli connection modify <UUID> ipv4.dns <dns_server_ip>
nmcli connection show <UUID>
nmcli connection up <UUID>

Use IMM or local console access where possible so you can recover safely if management connectivity is lost. Verify that the old appliance no longer owns the production IP before proceeding.

Step 4 — Assign the original IP to the new Console

On the new appliance, run the supported network setup wizard and configure the original IP and its associated network settings:

/opt/qradar/bin/qchange_netsetup

Save the configuration, exit the wizard, and verify reachability. Do not have both old and new appliances using the same address at the same time.

Step 5 — Transfer certificates and custom SSH material

From the old appliance, copy the trusted certificates and any required SSH/key material to the new Console. Treat private keys as sensitive credentials and restrict access to the transfer. IBM's examples include the following commands:

rsync -avz /opt/qradar/conf/trusted_certificates/ root@new_appliance:/opt/qradar/conf/trusted_certificates/
rsync -avz /etc/ssh/ root@new_appliance:/etc/ssh
rsync -avz /root/.ssh/ root@new_appliance:/root/.ssh

Replace new_appliance with the destination's reachable address. Do not blindly overwrite destination key material without checking the migration procedure and local security policy. If custom Console SSL certificates are used, follow IBM's certificate-installation workflow; copy certificate material to a staging location and use /opt/qradar/bin/install-ssl-cert.sh -i where the IBM procedure directs. Do not simply overwrite the new Console's HTTP certificate directory with files from the old appliance.

Step 6 — Restore configuration and deploy

  1. Copy the saved backup to /store/backupHost/inbound/ on the new Console.
  2. In the QRadar UI, open Admin → Backup and Recovery, select the backup, and restore the applicable configuration and data items as directed by the version-specific migration guide.
  3. Review restore results and resolve reported errors. Some restored license information may require new licenses to be installed on the replacement appliance.
  4. Run Admin → Advanced → Deploy Full Configuration and allow deployment to finish. Check host access and connectivity if the UI reports issues.

App data is handled separately from the configuration backup. Confirm the required apps/extensions are installed and restore their data using their own supported processes.

Step 7 — Transfer Ariel event and flow data

After the destination Console is configured, use IBM's syncAriel.sh process to transfer data under /store/ariel/. The utility transfers Ariel data; it does not move configuration or certificates. Obtain the script from IBM's linked migration/support documentation, validate that it is appropriate for the QRadar release, and use a persistent session such as tmux for a long transfer.

# On the old Console, in the directory containing the IBM-provided utility:
chmod +x syncAriel.sh
tmux
sh syncAriel.sh -i <new_Console_IP_address>

Monitor the transfer and review output/errors. IBM notes that this operation can be lengthy and transfers data in month-sized intervals to limit performance impact. If a transfer is interrupted, follow the script's documented rerun behavior rather than deleting files or improvising a manual sync.

Step 8 — If local Event Collector data exists

This is a separate, optional step for deployments where relevant data exists under /store/ec. It is not the same operation as syncAriel.sh. Follow IBM's procedure for stopping ecs-ec-ingress on the source and destination, creating the manual-stop marker on the destination, copying the relevant data, removing the marker, and restarting the service.

# Destination Console: prevent automatic restart, then stop ingress
touch /storetmp/ecs-ec-ingress.ecs-ec-ingress.manually_stopped
systemctl stop ecs-ec-ingress

# Copy the required /store/ec data from source to destination
# using the supported transfer method for your environment.

# Destination Console: remove marker and restart ingress
rm -f /storetmp/ecs-ec-ingress.ecs-ec-ingress.manually_stopped
systemctl start ecs-ec-ingress
Do not run the optional /store/ec procedure blindly.

Confirm the source contains the expected data, the exact copy path and ownership requirements, and that the IBM procedure for your QRadar release applies. The commands above show the control sequence, not a complete file-copy command.

4. Migrating to a new Console with a new IP address

Step 1 — Install the replacement Console at the planned new address

Install the new Console at a different IP address using a QRadar version/fix level that matches the existing deployment. Confirm the destination's role, hostname, network settings, software level, and reachability before starting the restore.

/opt/qradar/bin/myver

Step 2 — Create and stage the configuration backup

  1. On the old Console, create an On Demand Backup and wait for completion.
  2. Download the backup and keep a protected copy.
  3. Copy the backup to the new Console's /store/backupHost/inbound/ directory.
  4. Copy required certificates and custom-generated key material when the applicable IBM procedure calls for it. Include /root/.ssh as well as /etc/ssh where needed; do not expose private keys unnecessarily.

Step 3 — Restore the configuration and check managed-host access

Open Admin → Backup and Recovery on the new Console, select the backup, and follow the version-specific restore workflow. IBM's documented new-IP procedure includes a managed-host access check during restoration; it also instructs administrators to stop the host firewall service on managed hosts temporarily when required so that the Console can test access and restore the deployment.

Firewall-impact warning.

Stopping iptables affects the host's local firewall protections. Do not execute this across a production deployment without the IBM procedure open, change approval, an out-of-band access plan, and a clear step to restore the expected firewall/monitoring state. App Hosts have additional docker_iptables_monitor.timer considerations documented by IBM. Verify access is reported as OK before continuing.

# On an App Host, stop its firewall monitor timer first:
systemctl stop docker_iptables_monitor.timer
systemctl stop iptables

# On each other managed host:
systemctl stop iptables

In the restore workflow, use Test Hosts Access and confirm every managed host reports OK before continuing. If a host fails the access test, follow IBM's troubleshooting sequence for that host rather than proceeding with an incomplete deployment. At the end of the documented process, restore firewall and monitoring behavior for each host type; IBM specifically calls out restarting docker_iptables_monitor.timer on the App Host.

Complete the restore, review the results, and run Admin → Advanced → Deploy Full Configuration. Pay attention to installed applications versus deployment/extension configuration: those restore selections are not interchangeable, and app data still requires a separate plan.

Step 4 — Copy Ariel data to the new IP

Once configuration restore and deployment are complete, run the IBM-provided syncAriel.sh procedure from the old Console toward the new Console's IP address. Use the supported transfer workflow and a persistent shell session for long-running migrations:

chmod +x syncAriel.sh
tmux
sh syncAriel.sh -i <new_Console_IP_address>

Allow the transfer to finish, review errors, and confirm the expected historical event/flow data is available. Copying /store/ariel/ does not transfer configuration or certificates, and the basic QRadar configuration backup does not guarantee that app data is migrated.

Step 5 — Update integrations and network dependencies

Because the management IP is changing, review and update references to the old Console address or hostname, including DNS records, firewall rules, API clients, syslog destinations, monitoring, automation, certificates/SANs, external apps, and documentation. Some managed-host and integration settings are regenerated during deployment, but do not assume every third-party integration updates itself.

5. Important data-transfer distinctions

ItemHow it is handledCommon mistake
Configuration backupRestore through QRadar Backup and Recovery on a compatible matching version.Assuming a backup can be restored across arbitrary versions or fix levels.
Ariel event/flow dataTransfer using IBM's documented syncAriel.sh process.Assuming config restore brings all historical Ariel data or that syncAriel copies configuration.
Application dataBack up/restore using the instructions for each app or extension.Assuming apps and their databases are included completely in the QRadar configuration backup.
Certificates and key materialTransfer only the required material and re-install custom SSL certificates using the documented workflow.Blindly copying private keys into certificate directories or skipping trust validation.
Local /store/ec dataOptional separate operation when applicable; follow the release-specific Event Collector procedure.Confusing it with Ariel data, or stopping ingress without completing the marker/copy/restart workflow.

6. Post-migration validation and rollback

  • Confirm the replacement Console has the expected QRadar version, hostname, IP configuration, and license state.
  • Review Backup and Recovery restore results and complete a full configuration deployment without unresolved errors.
  • In Log Activity, run a recent-time search and verify new events are arriving and searchable.
  • In Network Activity, verify flows are being received and processed where flow collection is configured.
  • Check managed-host status, log source health, event pipeline, deployment health, time synchronization, and relevant System Notifications.
  • Verify certificates, custom trust, WinCollect, scanners, apps/extensions, API clients, and external integrations.
  • Confirm the historical Ariel data expected by stakeholders is present, and verify any relevant /store/ec data was migrated when applicable.
  • For a new-IP migration, validate DNS, routes, firewall allowlists, monitoring, and consumers of the old address.
  • Record transfer duration, skipped/failed items, final checks, and any service interruption. Keep the old Console powered down or isolated but available for the agreed rollback period.

If validation fails, do not bring the old and new appliances online with the same IP address at once. Follow the rollback plan to isolate the replacement, restore the old appliance's network settings if required, and bring it back only after confirming address ownership and the risk of configuration/data divergence.
