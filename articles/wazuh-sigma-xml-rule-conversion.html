Automated SigmaHQ to Wazuh
modular XML rule conversion

A focused CLI pipeline for translating selected SigmaHQ Windows detections into per-category Wazuh XML files—with explicit field mappings, persistent Rule IDs, and validation before deployment.

By Ashraf GamalUpdated 3 November 2026Wazuh 4.14.0 · Sigma · PythonApprox. 9 min read
In this guide

Field note: This article documents a focused conversion workflow and a Python prototype for a Wazuh 4.14.0 lab. It is not an official SigmaHQ or Wazuh backend. Conversion is a starting point for detection engineering—not proof that every Sigma rule is semantically equivalent after translation. Review and test each rule before enabling it in production.

1. Objective and scope

SigmaHQ provides vendor-neutral detection rules in YAML. Wazuh evaluates native XML rules against decoded event fields. A useful conversion workflow therefore needs more than a text substitution: it must map fields, preserve selection logic where supported, chain rules to the correct Wazuh parent rule, and assign IDs that remain stable across conversion runs.

This workflow deliberately starts with three Windows detection buckets that can be reviewed and tuned independently:

Conversion bucketSigma logsource categories / servicesOutput file
PowerShellps_script, ps_module, related PowerShell servicesSN_sigma_powershell.xml
Registryregistry_event, registry_add, registry_delete, registry_set, registry_renameSN_sigma_registry.xml
Network connectionnetwork_connectionSN_sigma_network_connection.xml
Excludedprocess_creation, file_eventNot generated by this run

The include-list is intentional: other Sigma categories are skipped rather than being sent through an unverified fallback. The converter also skips rules whose condition syntax, field names, or modifiers are outside its supported subset.

2. Conversion design and constraints

Custom Rule ID allocation

Wazuh recommends using IDs in the 100000–120000 range for custom rules. This workflow starts at 113000 and stores each Sigma rule UUID-to-Wazuh-ID assignment in sigma_rule_ids.json. Keep that file with the converter output and back it up: it is the state that preserves IDs when you run a later conversion batch.

Parent-rule mapping

Child rules should be chained to the built-in Wazuh rule that has already recognized the relevant event type. In the Wazuh Sysmon ruleset, Event ID 3 is represented by parent SID 61605; registry events use the Event IDs 12, 13 and 14 parents 61614, 61615 and 61616. The converter uses these mappings for the corresponding categories.

PowerShell needs more care. The correct parent depends on the PowerShell event channel and the exact rules shipped with the installed Wazuh version. Do not assume one SID applies to both Script Block Logging and module logging. Inspect the installed PowerShell ruleset, run a representative event through wazuh-logtest, and pass the verified parent SID for each PowerShell service with --parent-sid.

Boolean logic and value modifiers

In a Wazuh rule, multiple field conditions are cumulative. A Sigma list of values normally means “match any value”, while the Sigma all modifier means every value must match. The converter handles supported cases by combining alternative values into a PCRE2 alternation or emitting separate conditions for all. Simple and, or, 1 of, and all of selection patterns are supported; more complex expressions are skipped for manual translation.

The included prototype supports a limited set of string modifiers, including contains, startswith, endswith, windash, re, and cased. It does not claim full Sigma specification coverage.

3. Prerequisites

  • Ubuntu 22.04 or 24.04 build host with Python 3, Git, PyYAML, and xmllint.
  • Wazuh Manager 4.14.0 lab or test environment with administrative access for rule validation.
  • Windows endpoints forwarding the relevant Sysmon and PowerShell EventChannel telemetry.
  • A copy of existing custom XML rules so the converter can allocate IDs above the current maximum.
  • Representative raw events for every category you intend to validate.

Confirm that your installed decoder actually exposes the field paths used by the converter. The mappings in a Sigma rule and the fields produced by your Wazuh decoders are not automatically interchangeable.

4. Prepare the build workstation

sudo apt update
sudo apt install -y git python3 python3-yaml libxml2-utils

mkdir -p ~/sigma-wazuh-custom
cd ~/sigma-wazuh-custom

git clone --depth 1 https://github.com/SigmaHQ/sigma.git

Download the focused converter from the portfolio repository and make it executable:

cd ~/sigma-wazuh-custom
curl -fL \
  https://agamalx0.github.io/downloads/sigma2wazuh.py \
  -o sigma2wazuh.py
chmod +x sigma2wazuh.py
python3 -m py_compile sigma2wazuh.py

Download the sigma2wazuh.py converter. The script is intentionally conservative: it skips an unmapped Sigma field or an unsupported condition instead of silently converting it into a generic full-event text match.

5. Run the per-category conversion

Before converting, identify the parent rule IDs for the PowerShell services that exist in your environment. Inspect the installed ruleset on the Wazuh Manager and validate the event path using a real event. The values below are examples only—replace them with the SIDs verified on your manager.

# Keep the array empty until you have verified a PowerShell parent SID locally.
PARENT_ARGS=()
# Example only: uncomment and replace with the SID(s) verified on your manager.
# PARENT_ARGS=(--parent-sid "ps_script=" "ps_module=")

mkdir -p "$HOME/wazuh-existing-rules"
# Copy your existing custom rule XML files into this directory first.

./sigma2wazuh.py \
  --input "$HOME/sigma-wazuh-custom/sigma/rules/windows" \
  --output-dir "$HOME/sigma-wazuh-custom/output_xml" \
  --include powershell registry network_connection \
  --exclude process_creation file_event \
  --start-id 113000 \
  --group sigma_wazuh \
  --prefix "SN - " \
  "${PARENT_ARGS[@]}" \
  --existing-xml "$HOME/sigma-wazuh-custom/output_xml/*.xml" \
                "$HOME/wazuh-existing-rules/*.xml"

The parent-argument array is empty by default, so the converter will skip PowerShell rules until you add verified mappings. Configure only the services that exist in your environment; registry and network-connection rules can still be processed without PowerShell overrides.

Expected output files are separated by category:

output_xml/
├── SN_sigma_network_connection.xml
├── SN_sigma_powershell.xml
└── SN_sigma_registry.xml

sigma_rule_ids.json

The console summary reports how many Sigma documents were converted, how many Wazuh rules were emitted, which inputs were excluded, and how many rules were skipped as unsupported. A skipped rule is a review item—not a conversion failure to work around by weakening the mapping.

6. Validate generated XML locally

Validate every generated file before copying anything to the Wazuh Manager:

set -e
for file in ~/sigma-wazuh-custom/output_xml/SN_sigma_*.xml; do
  xmllint --noout "$file"
  printf '[OK] %s\n' "$(basename "$file")"
done

xmllint confirms XML well-formedness only. It does not validate Wazuh rule semantics, parent SIDs, decoded field names, PCRE2 behavior, or the detection outcome.

7. Stage and validate on Wazuh Manager

Back up the existing rules and transfer the candidate files to the manager. Use a staging directory first, then install the files under the custom rules directory:

# On the build workstation
scp ~/sigma-wazuh-custom/output_xml/SN_sigma_*.xml \
  user@<WAZUH_MANAGER_IP>:/tmp/

# On the Wazuh Manager
sudo install -o wazuh -g wazuh -m 660 \
  /tmp/SN_sigma_*.xml /var/ossec/etc/rules/

Run the Wazuh rule-engine configuration test before restarting the manager:

sudo /var/ossec/bin/wazuh-analysisd -t

If compilation fails, do not restart the manager. Review the reported file and line, correct the candidate XML, and repeat the test. Only restart after the analysis daemon test completes successfully:

sudo systemctl restart wazuh-manager
sudo systemctl is-active wazuh-manager

8. Validate detection logic with wazuh-logtest

Compilation does not prove a detection works. Run wazuh-logtest and feed it a representative event captured from an endpoint. The following is a Sysmon Event ID 3 field-shape example for a network connection; it is not a guaranteed match for a particular Sigma rule:

{"win":{"system":{"providerName":"Microsoft-Windows-Sysmon","eventID":"3","channel":"Microsoft-Windows-Sysmon/Operational","computer":"WKSTN-01"},"eventdata":{"image":"C:\\Windows\\System32\\WindowsPowerShell\\v1.0\\powershell.exe","sourceIp":"192.0.2.10","sourcePort":"51432","destinationIp":"203.0.113.10","destinationPort":"4444","protocol":"tcp","initiated":"true"}}}

For each rule you intend to enable, test both a matching event and a benign near-match. Review all three phases:

  • Phase 2: verify that the event is decoded and the expected win.system and win.eventdata fields are populated.
  • Parent match: confirm the expected Sysmon or PowerShell parent SID is reached for the event type.
  • Phase 3: confirm the custom Rule ID, SN - description, sigma_wazuh group, severity level, and MITRE ATT&CK ID where present.

In the Wazuh Dashboard, use the rule group to review the generated detections:

rule.groups: "sigma_wazuh"

Keep the test evidence with the rule file: Sigma source UUID, source filename, generated Rule ID, test event, expected result, observed result, and reviewer decision.

9. Known limitations and safe operating practices

  • Not a full Sigma backend: nested conditions, correlation rules, time windows, unsupported modifiers, and unmapped fields are skipped. Manual translation is required for unsupported rules.
  • Field maps are environment-dependent: validate each mapping against the JSON produced by your installed Wazuh decoder and the event sources actually collected.
  • Parent SIDs are version-sensitive: inspect the manager's local ruleset; do not assume a sample SID is valid for every Wazuh release or log channel.
  • Rule IDs require state: retain sigma_rule_ids.json, include existing custom XML files in the scan, and review IDs before merging outputs from multiple build hosts.
  • PCRE2 has operational cost: begin with a limited category set, test throughput and queue behavior, and tune noisy rules before broad deployment.
  • Keep rollback simple: deploy by category and disable one category file at a time if its detections create noise or performance pressure.

Do not treat a successful XML parse or a clean wazuh-analysisd -t result as approval for unattended deployment. The final acceptance criterion is correct matching against representative telemetry, with no unexpected matches against benign events.

10. Key lessons

  • Use an explicit category allowlist so an early conversion run stays within the scope you can validate.
  • Keep generated rules modular. Separate files make tuning, review, and rollback more controlled.
  • Preserve Sigma UUID-to-Wazuh Rule ID mappings across runs to avoid unnecessary ID churn.
  • Fail closed on unsupported fields and conditions. A skipped rule is safer than a rule that matches the wrong part of an event.
  • Validate the XML, Wazuh compilation, and actual event behavior as separate checks.
