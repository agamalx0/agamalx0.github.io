Automated Wazuh
daily healthcheck

A field note on turning repeatable Wazuh operational checks into an HTML report, a PDF attachment, and a scheduled email—so the SOC starts the day with a consistent view of platform health and issues that need attention.

By Ashraf GamalUpdated 28 October 2026Wazuh · n8n · GotenbergApprox. 8 min read
In this guideOverviewWorkflow at a glanceWhat the report showsConfiguration checklistTesting and validationSecurity and privacySharing the workflowTroubleshootingReferences

Scope: This article documents the workflow shown in my n8n execution and the accompanying healthcheck report. Node settings, remote commands, and host topology are deployment-specific; adapt and validate them in a test environment before use.

1. Overview

A SIEM can remain online while accumulating operational issues: disconnected agents, growing archives, storage pressure, service interruptions, or pipeline delays. A daily healthcheck makes these conditions easier to review consistently instead of relying only on occasional manual checks.

The workflow described here is called Wazuh Daily Healthcheck PDF over Email. It supports a manual execution for testing and a daily schedule. It gathers host and service information over SSH, builds a structured HTML report, converts that report to PDF with Gotenberg, and sends the PDF by email.

Example from the report

The captured run contained 43 checks: 41 passed and 2 warnings. The warnings were an oversized Wazuh log/archive directory and two disconnected agents. These are example snapshot values—not universal thresholds or expected results for every deployment.

3. What the generated report shows

The example report is designed to answer three questions quickly: is the monitoring stack responding, what needs attention, and where should the operator start investigating?

The following three images show additional pages from the actual generated healthcheck PDF. Each opens at its original resolution when selected.

  • Summary: total checks, passed checks, warnings, manager version, active agents, alert count, high-severity count, and disk utilization.
  • Component status: System, Manager, Agents, Dashboard, Indexer, and Pipeline.
  • Issues and actions: an issue description, severity/area, evidence, and a recommended next step.
  • Capacity detail: server resources, the largest disk-consuming directories, and the largest indices.
  • Activity: alerts over the previous 24 hours, top agents, top rules, and disconnected agents.
  • Check results: service state, listening ports, queues, event ingestion, Filebeat output, indexer cluster/disk/heap, and selected log/error checks.

In the captured run, the report showed 10 of 12 agents active, 200 alerts in 24 hours, 26 high-severity alerts, and 76% highest filesystem usage. The manager log path was 116.3 GB, including 115.5 GB of archives; the indexer disk check showed 76.5% used with 161.4 GB free. Treat these figures as a dated snapshot, not a sizing recommendation.

Example issue: archive growth

The report flags a large raw event archive. Before changing logall, logall_json, or archive retention, check retention obligations, forensic requirements, compliance policy, and whether raw event archives are used by downstream searches. Do not automate deletion of archived logs as a default remediation.

Example issue: disconnected agents

The report identifies two disconnected agents and recommends checking the endpoint agent service, manager reachability (including TCP 1514 where appropriate), and the agent key. Confirm whether an endpoint was intentionally decommissioned before removing it from agent management.

4. Configuration checklist

The exact settings depend on the environment. Review these items before enabling a scheduled run:

  1. n8n runtime: use a supported, maintained n8n deployment and restrict access to the editor.
  2. Timezone and schedule: confirm when the daily trigger should run in the intended local timezone.
  3. SSH credentials: configure a dedicated credential for each target host in n8n. Do not place passwords or private keys in node code.
  4. Command access: test each command interactively with the intended account. If a command requires privilege elevation, explicitly configure and audit the permitted command path instead of granting broad unrestricted sudo access.
  5. Host topology: configure only the SSH nodes that correspond to real roles in your deployment. A single-host, all-in-one environment differs from a distributed Wazuh architecture.
  6. Report configuration: confirm client label, host labels, thresholds, check output parsing, date/time formatting, and the meaning of each “OK”, “WARNING”, or “N/A” state.
  7. Gotenberg: configure the reachable base URL and the HTML-to-PDF route. Keep the service on a trusted network and do not expose it publicly without a strong reason and appropriate controls.
  8. Email delivery: set SMTP/provider credentials in n8n, test the recipient list, and verify the message subject, report name, attachment, and delivery result.

5. Test before scheduling

  1. Run the workflow manually against a test or non-critical environment first.
  2. Open the execution and inspect each node’s input and output. Confirm SSH commands returned valid evidence and that command failures are surfaced as failures or warnings.
  3. Review the HTML output for escaped text, readable tables, missing values, accurate timestamps, and sensible page breaks.
  4. Check that the PDF opens and contains the same metrics and issue details as the HTML report.
  5. Verify email delivery and confirm the attachment is the expected PDF—not an HTML error page or empty binary.
  6. Simulate or safely reproduce at least one warning to ensure warning status and remediation text appear correctly.
  7. Only after the manual run passes review, enable the daily schedule and monitor its first scheduled executions.
Success criteria

A green n8n execution by itself is not sufficient. The final check is that the report accurately reflects its collected data, converts to a readable PDF, and is delivered to the intended recipients.

6. Security and privacy before publishing or operating

  • Use dedicated SSH identities with least privilege and restrict network reachability to the required systems.
  • Keep credentials in n8n’s credential store. Never commit passwords, tokens, private keys, SMTP secrets, or real credential IDs/names intended only for your instance.
  • Sanitize workflow exports, screenshots, execution logs, generated HTML/PDF files, hostnames, internal IP addresses, email addresses, usernames, and agent identifiers before publishing.
  • Review SSH command output and email recipients: reports may reveal service versions, host inventory, alert volume, internal paths, and operational weaknesses.
  • Store reports according to your organization’s retention and data-classification requirements. Restrict the mailbox and any archive where PDFs are kept.
  • Use read-only collection by default. Keep destructive cleanup, configuration changes, and service restarts out of an automated healthcheck unless separately approved and change-controlled.

7. Sharing a reusable workflow export

n8n workflows can be exported and imported as JSON. A screenshot or this article is not an importable workflow by itself. Before publishing a companion JSON export, remove instance-specific settings, sanitize hostnames and recipient addresses, and check node parameters, credential references, expressions, and any embedded code for sensitive data.

Workflow export is not currently available

The earlier downloads/wazuh-healthcheck-ssh.json file was incomplete: it ended after the Config node and did not contain the remaining nodes, connections, or closing JSON structure. That incomplete export has been removed rather than advertised as an importable download. Export the complete workflow from n8n, validate the JSON, and review all credentials and environment-specific values before publishing it.

Also confirm the schedule before release: the historical export used 5 14 * * * (14:05), while the pictured workflow shows Daily 12:00 AM.

When a complete export is published, readers can download it, choose Import from File in n8n, configure credentials and environment-specific values, and test manually. Review every node and email recipient before activating the workflow. Credentials usually need to be configured in the target n8n instance rather than expected to transfer with an export.

Decide and state a license for the workflow file before inviting public reuse. Making a file public does not by itself establish permission to redistribute or adapt it.
