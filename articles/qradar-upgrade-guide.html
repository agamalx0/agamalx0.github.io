IBM QRadar upgrade guide:
planning, execution & validation

A comprehensive, operations-focused guide to preparing and executing a QRadar SIEM software upgrade. It covers version-path selection, pre-upgrade checks, backups, HA and distributed deployments, SFS/ISO choices, execution, post-upgrade validation, and failure handling.

Read this first: there is no universal QRadar upgrade path.

Always identify the exact source version, fix pack/update package, interim fix, deployment model, and target release. Then follow IBM's supported path for that precise combination. Do not assume that the newest SFS can upgrade every earlier version, or that a successful upgrade on one host makes an out-of-sync deployment supported.

Scope and safety

This article is a planning and validation runbook for administrators upgrading an existing IBM QRadar SIEM deployment. It is not a substitute for the release-specific IBM Upgrade Guide, SFS/ISO release notes, or the applicable support advisories. File names, command options, minimum source levels, required free space, installer menus, and known issues vary by release.

An upgrade can affect event ingestion, searches, offenses, apps, integrations, HA synchronization, and the OS underneath QRadar. Schedule an approved maintenance window, ensure the people responsible for network, infrastructure, SOC operations, and recovery are available, and agree on success criteria before starting.

1. Confirm the supported upgrade path

Start by recording the exact installed version and fix level. In the UI, use Help → About. From the CLI, the QRadar version tool is documented as:

/opt/qradar/bin/myver -v

Record this output for the Console and each managed host as needed. Then review the current target release notes, the upgrade guide, known issues, and IBM's upgrade-path documentation. Check hardware/memory requirements, supported hypervisor or appliance model, required intermediate updates, OS migration prerequisites, HA constraints, application compatibility, and any product exclusions.

Current path examples — documentation checked on 11 October 2026

These examples illustrate why the path must be confirmed; they are not a generic upgrade recipe.

  • IBM's QRadar 7.6.0 Fix Pack 5 SFS notes list QRadar 7.6.0 FP1, FP2, FP3, and FP4 as supported source versions for that SFS.
  • IBM's QRadar 7.6.0 Fix Pack 1 notes list selected QRadar 7.5.0 UP10–UP15 sources, with eligible interim fixes, as supported sources for FP1.
  • IBM's QRadar 7.5.0 UP16 notes say UP16 cannot upgrade directly to the 7.6.0 stream under the published path. Do not attempt a direct jump unless newer IBM guidance explicitly supports it.
  • QRadar Incident Forensics is not available in the 7.6.x release stream according to IBM's 7.6.0 release notice. If your deployment relies on it, resolve the product compatibility decision before choosing 7.6.x.

Verify these conditions again against the exact files available in Fix Central and the latest release notes on the day of your change.

Useful starting points: QRadar 101 — Installs and Upgrades, QRadar 7.6.0 upgrade preparation checklist, and IBM Support — legacy upgrade paths.

2. Understand the upgrade media: ISO versus SFS

MediaTypical roleWhat to verify
SFS software updateFix packs/update packages that do not require a major operating-system version upgrade.Exact source versions supported by the SFS, required disk space, checksum/signature validation, and any package-specific prerequisites.
ISO upgradeMajor upgrade paths that include an operating-system version change, where IBM directs administrators to use ISO media.Source version requirements, OS migration constraints, device drivers, encryption support, boot/installer process, and hardware/VM compatibility.

Do not pick a file based only on its extension or filename. IBM's upgrade checklist states that ISO files are used for major OS version upgrades and SFS files for updates that do not include a major OS version upgrade. The target release instructions decide which media and sequence apply.

3. Plan the change window

Build a short change plan before touching the Console. At minimum, it should contain:

  • Source version and target version, supported path reference, release notes, and approved SFS/ISO filename.
  • Impacted systems, expected outage/degraded-service window, upgrade order, responsibilities, and communications to SOC stakeholders.
  • Backup location, restoration/recovery owner, decision points for aborting, and a recovery procedure that is actually viable for the source/target versions.
  • Pre-upgrade health status and baseline measurements so post-upgrade results can be compared with a known-good state.
  • Application, integration, custom content, certificate, network, HA, and log-source checks required after the update.

Do not estimate downtime only from installer progress. Some upgrades include database migrations or OS changes and can take many hours depending on database size, I/O performance, network performance, and hardware. Allocate a window with enough margin for validation and escalation.

4. Complete the pre-upgrade checklist

Version, release notes, and compatibility

  • Confirm the exact source version on the Console and managed hosts.
  • Verify the target package's supported source versions and every required intermediate step.
  • Read target release notes, known issues, product notices, hardware/memory requirements, browser requirements, and any OS migration notes.
  • Confirm all QRadar products and appliance roles in the deployment are supported for the target release.
  • Inventory App Host and application framework dependencies; update apps and confirm they are not in an error state.
  • Review integrations and dependencies such as WinCollect, custom DSMs, custom rules, scripts, certificates, routing, external authentication, and API clients.

Health and deployment state

  • Run the version-appropriate QRadar health checks and remediate blockers first.
  • Review System Notifications for event-pipeline/performance degradation, memory issues, TX sentry/process stopped events, HA active/standby failures, disk or unavailable partition issues, time synchronization, backup failures, replication problems, and RAID/controller warnings.
  • Verify time synchronization and basic network connectivity between the Console and managed hosts.
  • Ensure pending configuration changes have been deployed successfully.
  • Confirm there are no unresolved deployment or managed-host synchronization problems.
  • Confirm storage/filesystems have adequate free space according to the exact package notes. Avoid filling /storetmp, /tmp, /store/transient, or other required partitions with upload files or logs.
  • Check hardware health, RAID, CPU, memory, filesystem capacity, and underlying hypervisor/storage alerts where applicable.

Deployment-specific checks

  • For older QRadar Event Collector deployments, confirm whether a GlusterFS-to-DRBD migration or other prerequisite is required by the selected version path.
  • For HA, validate active/standby health, synchronization, required filesystem mount states, and the documented HA upgrade procedure.
  • For major OS upgrades, check unsupported device drivers, encryption limitations, and any OS migration pretests called out by IBM.
  • Confirm long-running scans and reports have completed or are handled according to the target release's upgrade notes.
  • Close active QRadar UI sessions if the target release notes require it, to avoid installer/log access issues.

Deployment inventory and housekeeping

Capture an appliance inventory and confirm that all hosts are at the expected source version before beginning:

# Inventory appliance names and IP addresses
/opt/qradar/support/deployment_info.sh

# Compare software versions across appliances
/opt/qradar/support/all_servers.sh -C -k /opt/qradar/bin/myver > myver_output.txt
cat myver_output.txt
  • Check /root and approved operational directories for local scripts, personal utilities, exports, support-provided JAR files or interim fixes, and other files that are not part of the standard QRadar installation.
  • Preserve custom network configuration. On systems that use the legacy RHEL network-scripts layout, static routes may be stored in /etc/sysconfig/network-scripts/route-<interface>; other OS versions may use a different NetworkManager configuration. Record the actual configuration for the installed OS instead of assuming one path applies everywhere.
  • On physical appliances, verify firmware and hardware health against IBM's appliance-specific guidance: QRadar firmware list for supported xSeries appliances.
  • Review mounted storage with mount | column -t and df -Th. Follow the target upgrade guide for external-storage requirements; IBM's checklist generally instructs administrators to unmount external storage other than /store or /store/ariel. Do not unmount required QRadar filesystems or storage used by an active process.
  • Confirm previous update media is not still mounted. Only when no installer or upgrade is active and after confirming the mount targets are stale, use the documented per-deployment cleanup commands where appropriate.
/opt/qradar/support/all_servers.sh -k "umount /media/cdrom"
/opt/qradar/support/all_servers.sh -k "umount /media/updates"
Fleet-wide command caution

all_servers.sh executes commands across appliances. Review the target list, ensure no upgrade is running, and confirm the mounts are stale before issuing fleet-wide unmount commands. Do not run these commands blindly.

IBM's pre-upgrade checklist is authoritative for the chosen target. See Preparation checklist for QRadar upgrades and QRadar software update checklist for administrators.

5. Backup and recovery planning

Do not begin an upgrade until the latest configuration backup has completed successfully and its file is copied to a safe location outside the system being upgraded. Verify that the backup is readable, that retention and access controls are appropriate, and that the team understands how recovery would work.

  • Take a QRadar configuration backup using the supported Backup and Recovery workflow. Download the completed backup file rather than relying solely on a file left on the appliance.
  • Follow IBM's documented data backup/recovery procedure for your product version and environment. Configuration backups do not automatically include every app's persistent data.
  • Back up app data on the Console and/or App Host where the apps actually reside. IBM documents app-volume-backup.py for this purpose. Take a fresh manual backup after any important app changes and list the resulting archives:
cd /opt/qradar/bin
./app-volume-backup.py backup
./app-volume-backup.py ls

The supported listing subcommand is ls (not lsc). IBM notes that a configuration backup does not back up apps' data; consult Backing up and restoring app data for the exact release. Keep the backup archive outside the system being upgraded.

  • Export QRadar custom content before the upgrade. IBM documents the following Content Management Tool command, which may take a long time in larger environments:
/opt/qradar/bin/contentManagement.pl --action export --content-type all

Store the export in a safe location and allow enough time for completion. For large deployments, an export can take many hours or longer. Keep a record of the export path and completion status.

  • Preserve third-party and locally managed artifacts such as custom DSMs, rules, reference data configurations, scripts, certificates, integration settings, support-provided JAR files/interim fixes, personal utilities, exports, and any custom network configuration.
  • Know where upgrade logs, precheck output, and existing deployment documentation will be stored.
  • Confirm the recovery plan, recovery time objective, decision owner, and support contacts before the window begins.
Do not treat a live copy of /store/ariel as a universal backup method.

The original notes include generic cp, rsync, and scp examples for event data. Do not copy active Ariel storage ad hoc as a substitute for a supported QRadar backup or migration procedure: it can be large, change while being copied, and may not provide a consistent, restorable backup. Use a specifically documented IBM data-migration procedure only when it applies to your scenario.

A configuration backup is not automatically a downgrade/rollback mechanism.

QRadar configuration backups can have version compatibility limits. Do not assume a backup created on one version can be restored to an older or different version. Confirm restoration constraints in the specific migration/recovery guide, and arrange a supported recovery strategy for the source and target versions.

6. Managed hosts, deployment order, and HA

IBM's QRadar upgrade instructions require the Console to be upgraded first, followed by managed hosts, and require all QRadar products in the deployment to reach the same supported version and fix level. Follow the target release's exact order and patch-installer options rather than inventing a host order.

Distributed deployments

  • Inventory all host roles: Console, Event Collectors, Event Processors, Flow Processors, QFlow Collectors, Data Nodes, App Hosts, QRadar Network Insights, Incident Forensics, and any other attached QRadar products.
  • Upgrade the Console first, then the hosts selected by the supported installer workflow. Some host roles can be updated concurrently; that does not mean every appliance should be upgraded in arbitrary order.
  • If a host is unreachable or incompatible, stop and resolve it according to the installer and target release instructions. Do not knowingly leave a mixed-version deployment.
  • After the upgrade, use supported tools such as validate_ecs_services.sh and deployment inventory checks where appropriate to confirm service versions and managed-host communication.

High availability

  • Verify the primary appliance is Active and the secondary is Standby, and confirm synchronization before starting.
  • Before the change, verify that /store is mounted on the primary but not on the secondary, and that /transient is mounted on both hosts, as required by the applicable HA upgrade checklist.
  • Capture the relevant mount state using mount, df -Th, and the HA status tools prescribed for the release. Do not manually change mount state to make it match a checklist.
  • Follow the HA upgrade process documented for the exact release. IBM's instructions note that upgrading an HA primary can automatically upgrade the HA secondary for supported paths.
  • Do not manually force HA failover during patching or a software upgrade unless the applicable IBM procedure explicitly directs it.
  • Keep any version-specific file-copy procedure—such as a workaround involving map_localhost_interfaces.txt—out of the general runbook. Perform it only when the exact IBM procedure for the selected upgrade path requires it.
  • Afterward, verify cluster roles, synchronization, storage/VIP behavior, and event processing before closing the change.

References: Upgrading QRadar SIEM, Parallel patching, and Manual HA failovers.

7. Download and validate the software

  1. Download the exact SFS or ISO specified by IBM for the approved target path from IBM Fix Central.
  2. Read the specific package's release notes and installation instructions—not an article for a different fix pack.
  3. Verify the SHA-256 checksum against the value published by IBM. Where IBM provides a code-signature validation utility or requires a specific utility version, use the version listed in the target package notes.
  4. Transfer the package securely to the supported staging directory. Do not rename the SFS file if the parallel patching workflow requires its original filename.
  5. Use the package instructions to confirm free space. For example, the QRadar 7.6.0 Fix Pack 5 note requests at least 5 GB in the relevant temporary/store temporary space on the Console and documents a disk-space check.

Example precheck pattern documented in the 7.6.0 Fix Pack 5 instructions:

df -h /tmp /storetmp /store/transient | tee diskchecks.txt

This check is an example for that release's procedure, not a replacement for verifying required filesystems and free-space requirements on every host.

8. Execute the upgrade

The exact command sequence depends on the selected SFS/ISO package. For SFS-based QRadar software updates, IBM's release instructions commonly use a mounted SFS file and the included installer, but always use the exact filename, mount point, and sequence in the target release notes.

First stage the exact SFS file in the directory required by the release notes (commonly /storetmp for the documented releases), check filesystem capacity, and verify the package digest:

# Replace the filename with the exact file downloaded from Fix Central
df -h /tmp /storetmp /store/transient | tee diskchecks.txt
sha256sum /storetmp/<exact-target-file>.sfs

Compare the SHA-256 output with the digest published by IBM for that exact package. Do not rely only on the MD5 checksum mentioned in older notes when IBM publishes SHA-256. Do not proceed if the digest differs.

An example for the documented QRadar 7.6.0 Fix Pack 5 SFS workflow is:

# Example only: replace the filename with the exact downloaded SFS.
# Run only if it matches the target package's official instructions.
mkdir -p /media/updates
mount -o loop /storetmp/760-QRADAR-QRSIEM-2026.4.0.20261002130537.sfs /media/updates

# Optional pretest, only when supported by this release/package
/media/updates/installer -t

# Start the installer only after all pretests pass
/media/updates/installer
Do not copy this example as-is for a different release.

The SFS filename above is specific to QRadar 7.6.0 Fix Pack 5. Other versions use different filenames and may have different prerequisites, supported source levels, installer options, and pretests. The -t option is the installer pretest mode documented for supported packages; follow the target release notes. During pretesting, certain services such as the web server and HostContext may be stopped and restarted automatically. If a pretest fails, resolve the reported issue and rerun the test; do not continue to patch with a failed pretest.

When the installer opens, read all pre-installation checks and prompts. Choose the sequential/legacy or parallel method only if it is offered and supported for the selected package and deployment. Follow the installer’s guidance about patching the Console first and updating eligible managed hosts afterward.

Sequential versus parallel patching

  • Sequential: patches hosts in a controlled sequence. It can be easier to follow for deployments where staged troubleshooting is preferred, though the maintenance window may be longer.
  • Parallel: where supported, stages the package and upgrades eligible hosts concurrently after the Console step. Review the target release’s rules, unreachable-host behavior, and progress/status reporting before choosing it.

Parallel patching is not a way to bypass compatibility or host-order restrictions. Follow the current IBM parallel-patching guide and do not rename the SFS file where the procedure says its original name is required.

9. Monitor the upgrade; do not interrupt it casually

  • Keep an active administrative session and a separate method to reconnect if the SSH client drops. If the installer uses a persistent session such as tmux, follow the package instructions for reconnecting.
  • Monitor the installer output and status/report options where provided. Record the start time, prompts, warnings, host-by-host progress, and failures.
  • Be aware that some upgrade phases—especially database migration or large ownership/permission changes—can appear idle for a long time. Check target release notes and logs before concluding the installer is hung.
  • Do not reboot, kill processes, unmount update media, or start a second installer merely because there is no immediate progress message. Interrupt only under a documented recovery procedure or after an informed decision with IBM Support.
  • Review the final summary for managed hosts that were skipped or not updated. Investigate each result; a success message from the Console alone does not prove every managed host is patched.

10. Post-upgrade validation

Do not close the maintenance window when the installer exits. Validate the QRadar product, data pipeline, integrations, and operational behavior against the baseline recorded before the change.

Release-specific finalization

  • Run the documented post-upgrade health check for the release. Where supported, drq -v provides verbose local-host health-check output; run the appropriate checks on the relevant hosts and address reported failures.
  • For SFS update procedures that call for it, unmount the update media after the installer has finished and the system is stable. Do not unmount media while the installer is active:
umount /media/updates

Delete the staged SFS only after successful completion and after confirming it is not needed for diagnostics or a supported retry. Clear the browser cache when the target release notes instruct you to. If the release workflow calls for checking Auto Update from the Console Dashboard/Admin UI after the upgrade, verify update status there; this is a release-specific finalization step, not a replacement for the software upgrade itself.

Platform and deployment

  • Confirm the expected QRadar version and fix level on the Console and each managed host (for example, using /opt/qradar/bin/myver -v).
  • Review the installer result and list of hosts updated, skipped, or failed.
  • Run the release-appropriate health checks and review new System Notifications.
  • Verify managed-host connectivity and ECS/ECS-Ingress service versions with supported diagnostic tools where applicable.
  • Check HA roles, synchronization, filesystem mount state, VIP/shared network behavior, and replication health if the deployment uses HA.
  • Clear the browser cache before logging in if the target update instructions require it.

SOC functionality and data

  • Verify log sources are communicating and new events are searchable with current timestamps.
  • Verify network flows are arriving if flow data is part of the deployment.
  • Confirm offenses are being generated as expected, and run a known-good test/search aligned to your local detection validation process.
  • Check custom DSMs, rules, reference data, saved searches, reports, dashboards, and scheduled tasks most important to SOC operations.
  • Verify apps are running, compatible, and no longer reporting error states. Test App Host applications when present.
  • Test integrations such as SOAR/case management, threat intelligence, ticketing, authentication, email, API clients, and external data sources.
  • Confirm scheduled configuration backups and any other critical operational jobs are functioning.
  • Record before/after EPS/FPM, event pipeline health, storage usage, search latency, and other workload-specific baselines.
Close the change only when acceptance criteria pass.

At minimum, all intended hosts should be on the supported version, health checks should be acceptable, core log and flow ingestion should be confirmed, critical applications and integrations should work, and any remaining warnings should have documented owners and plans.

11. If an upgrade fails or a host is left behind

  1. Pause additional manual changes. Do not attempt an improvised downgrade or rerun a different installer over the failed state.
  2. Capture the full installer summary and exact error, timestamps, QRadar versions, host role, free-space output, relevant system notifications, and logs specified in the target upgrade guide.
  3. Determine whether the Console completed and which managed hosts did not; do not assume a failed message on one host means all hosts failed—or that the rest are healthy.
  4. Follow the version-specific IBM procedure for retrying or upgrading a skipped host. IBM release notes sometimes permit copying the package to the affected host and running the installer locally, but use that method only when the exact package documentation says it is supported.
  5. For database migration stalls, service startup issues, HA/DRBD synchronization problems, or a suspected damaged upgrade, preserve evidence and escalate using IBM's documented troubleshooting or support process before risky repairs.
  6. If recovery or rollback is required, use the recovery plan agreed before the change. Confirm version compatibility, supported restore sequence, and impact to event/flow data before acting.

For diagnostics, refer to Part 4 — QRadar Troubleshooting and Part 3 — QRadar Health Check. These are companion references, not substitutes for the release-specific upgrade instructions.

12. Copyable change checklist

  • Source version and all host versions recorded.
  • Supported target path verified in IBM release notes.
  • Target-specific restrictions, known issues, OS, hardware, app, and HA requirements reviewed.
  • Health checks passed; critical warnings fixed; deployment changes applied.
  • Capacity, disk space, network/time sync, backup and replication status verified.
  • Configuration backup completed, downloaded, and recovery plan confirmed.
  • App data backed up separately where required; custom content export completed and copied off-host.
  • Deployment inventory/version output saved; custom scripts, static routes, firmware, external storage, and previous update mounts reviewed.
  • SFS SHA-256 verified against IBM's published digest; pretest passed where supported.
  • Apps and integrations reviewed for target compatibility.
  • Correct SFS/ISO downloaded, checksum/signature verified, and free space checked.
  • Change window approved; SOC, IT, application, and recovery contacts available.
  • Console and managed hosts updated according to the documented sequence.
  • Failed/skipped host summary reconciled; every host on the required version.
  • Health, HA, ingestion, searches, offenses, reports, apps, and integrations validated.
  • Upgrade evidence, versions, deviations, and closure notes recorded.
