Designing a multi-tenant Wazuh MSSP:
AD, LDAPS, RBAC and document-level security

A reference architecture for separating Client A, Client B, and SOC-operations data in a shared Wazuh platform—using Active Directory groups for identity, OpenSearch roles and document-level security for data access, and dashboard tenants for customer-specific saved objects.

1. Scope and what the evidence supports

The goal is to host multiple customers in one Wazuh deployment without allowing one customer to read another customer's alerts. The supplied diagram describes three identity populations: Client A users, Client B users, and privileged SOC/MSSP operators. It also shows a workspace for each customer and an SOC-operations workspace for cross-customer investigation.

The surviving overview and screenshot labels identify evidence for AD groups and users, LDAP authentication/group lookup on the Wazuh side, an MSSP login page, separate Client A and Client B views, an attempt by Client A to reach Client B data, and an operator's available tenants. These screens can document behavior of the tested lab; by themselves, they do not prove every setting on disk or every possible bypass path.

3. Access model: identity, data and workspace are separate controls

A safe design applies three distinct controls: authentication proves who signed in; indexer permissions determine which documents that identity can read; tenant permissions determine which saved dashboards and searches the user can access or edit. OpenSearch defines DLS as a read/search control and documents that writes are governed separately by index permissions. OpenSearch DLS documentation ↗

Critical isolation rule: Do not rely on tenant names, saved searches, dashboard filters, hidden menu items or Wazuh agent-group UI to enforce customer separation. Isolation must be enforced by indexer permissions and a verified document-level filter on every index that contains customer data.

4. Configure Active Directory and LDAPS

  1. Create dedicated groups. Keep Client A, Client B and SOC operator membership separate. Avoid putting customer users into shared administrator groups.
  2. Use LDAPS. Configure the Wazuh Indexer's LDAP authentication and authorization backends to connect to the AD FQDN on port 636. Trust the correct CA chain and keep hostname verification enabled.
  3. Use a least-privileged bind account. It needs to read the user/group attributes required for authentication and role lookup, not administer the domain.
  4. Map group membership into backend roles. The exact userbase, usersearch, rolebase, rolesearch and group attributes depend on AD schema and nesting. Validate that a test user returns only the expected backend roles.
  5. Map backend roles to indexer roles. A directory group is not automatically an indexer permission. Create explicit mappings and check inherited memberships so a client user cannot receive a broad operator/admin role through another group.

Back up security configuration and keep a rollback path before making changes. Wazuh's LDAP guide covers the indexer authentication (authc) and authorization (authz) blocks, role lookup, backend-role mappings and dashboard role mapping. Follow the procedure for the installed release rather than copying a block from another version unchanged. Wazuh Active Directory and LDAP integration ↗

A useful transport check from the Indexer host is:

openssl s_client \
  -connect <AD_FQDN>:636 \
  -servername <AD_FQDN> \
  -CAfile <PATH_TO_TRUSTED_AD_CA> \
  -verify_return_error

Replace the placeholders with your environment's values. A successful TCP connection alone is not enough: verify chain validation, hostname matching, DNS and group lookup. Never put the bind password or other secrets in a public GitHub repository.

5. Label customer telemetry consistently

DLS can filter only on fields that exist in indexed documents. Wazuh's documented group-restricted access example uses agent.labels.group for alerts. A centralized agent configuration can add a label like this to a customer's agents:

<agent_config>
  <labels>
    <label key="group">client-a</label>
  </labels>
</agent_config>

Use a distinct label for Client B and the SOC-operations environment. Before writing a DLS query, inspect a real alert and confirm the field path and exact value. Newly configured labels appear in new alerts; historical alerts may not have the field.

Do not assume an agent-management group name is automatically present in every alert document. Agent groups help manage configurations. The indexed label used by DLS is a separate data attribute that must be tested. Monitoring and other indexes can use different schemas, so inspect them and design their filters separately.

6. Create per-customer indexer roles and DLS filters

For a read-only Client A role, limit index permissions to the required patterns (for example, wazuh-alerts-*), the necessary read actions, and a DLS query selecting Client A's label. An illustrative DLS query is:

{
  "bool": {
    "must": [
      {
        "match": {
          "agent.labels.group": "client-a"
        }
      }
    ]
  }
}

For Client B, use its own verified label value, such as client-b. This is the query body for the DLS setting, not a complete role definition. Configure index patterns, cluster permissions, tenant permissions and other operational indexes separately.

  • Grant only required read/search permissions. Do not grant customer roles write, update, delete or broad cluster-admin actions.
  • Apply customer scope to every index that may expose customer information. Monitoring or agent-inventory indexes may use a different field path than alert documents.
  • Keep the SOC operator role separate. If cross-customer investigation is required, grant it the explicit data scope the SOC is authorized to access; do not reuse this role for customers.
  • Audit every role each user receives. OpenSearch combines DLS queries from multiple roles with OR logic; an additional broad or unfiltered role can undermine the intended separation.

7. Create dashboard tenants for each audience

Use dedicated tenants/workspaces for Client A, Client B and SOC operations. Assign each role access only to the appropriate tenant, and choose read-only or read-write access depending on whether users may save or edit dashboards. OpenSearch tenants store dashboard objects such as saved dashboards, visualizations and index patterns/data views; they do not independently isolate the alert documents. OpenSearch multi-tenancy overview ↗

Configure the UI layer after the indexer data controls work. A Client A user must still be unable to query Client B documents through Discover, another index pattern, a direct search URL or an API request made with that user's identity. Similarly, placing a SOC dashboard inside the SOC-operations tenant does not prevent Client A from reading SOC documents if indexer permissions are too broad.

8. Validate isolation with positive and negative tests

Use separate test accounts for Client A, Client B and SOC operators. Run tests as those users, not only as an administrator who can bypass restrictions. Capture both what a user can see and what the user must not see.

Record the test date, account role, index pattern, query, expected result, actual result and pass/fail outcome. An empty result or a forbidden response may both be valid denial behavior depending on configuration, but the test must show that another customer's records were not returned.

9. Troubleshooting and failure modes

  • Login works but access is wrong: inspect returned backend roles, role mappings, indexer roles and tenant permissions separately. Successful LDAP authentication does not prove authorization is correct.
  • Client A sees no results: inspect an actual alert's source fields. Confirm the DLS field/value, read permission, index pattern and whether the alert contains the label.
  • Client A can see Client B: suspend use of the account for normal analysis while investigating. Review every inherited role, look for broad/unfiltered index permissions, inspect DLS on each relevant index and retest cross-customer queries.
  • LDAPS group lookup fails: check DNS/FQDN, TCP 636, CA trust, hostname verification, bind-account permissions, search bases, group attributes and nested-group behavior.
  • Old alerts do not filter: historical documents may lack newly configured labels. Plan an approved version-appropriate backfill/reindex or document the history gap; do not claim full isolation until old-data paths are addressed.
  • Dashboards appear in the wrong tenant: review tenant permissions and which tenant was selected when the saved object was created. Fix the workspace mapping without weakening indexer data isolation.

10. Production-readiness checklist

  • Use a supported and matched Wazuh component set; review release notes before patching.
  • Keep LDAP bind credentials, admin keys and other secrets outside the website and Git repository.
  • Validate LDAPS certificates, verify hostnames, restrict network paths, and do not expose Indexer/API endpoints publicly without a deliberate security design.
  • Keep customer roles read-only and least-privileged; do not map client groups to broad administrator roles.
  • Verify DLS covers alert data and every additional index exposed to clients.
  • Test multiple-group membership, nested groups, disabled accounts and revoked membership.
  • Repeat isolation tests after changes to roles, labels, data schema or Wazuh/OpenSearch versions.
  • Plan backups/snapshots, retention, capacity, monitoring and recovery. The supplied single-node diagram is not a high-availability architecture.
