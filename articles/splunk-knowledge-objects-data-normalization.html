Splunk Knowledge Objects & Data Normalization

A reusable workflow for standardizing fields, enriching events with asset context, simplifying searches, and grouping related security data.

By Ashraf GamalUpdated 17 November 2026Splunk · SIEM EngineeringApprox. 9 min read
In this guide 1. Confirm data and source fields 2. Normalize field names 3. Enrich events with an asset lookup 4. Reuse searches with macros 5. Classify events with event types and tags 6. Validate and maintain the knowledge layer
What you'll build

This guide shows how to use Splunk knowledge objects to normalize field names, add asset context, standardize repeated searches, and categorize related events. The steps are reusable; the indexes, sourcetypes, fields, and object names below are examples. Confirm and substitute the values from your own environment.

1. Confirm data and source fields

Before creating knowledge objects, confirm that the expected events are indexed and identify the fields Splunk extracts. The examples in this guide use Windows Sysmon and FortiGate traffic:

SourceExample indexExample sourcetype
Windows SysmonwineventlogXmlWinEventLog
FortiGate trafficnetworkfortigate_traffic

Start with a narrow search and check the field names in representative events. Your environment may use different indexes, sourcetypes, add-ons, or field names, so verify these before copying a search. If no events return, check the time range, ingestion path, permissions, and event metadata first.

The screenshots show particular runs of a lab dataset. Their event counts and timestamps are examples, not expected values; results will vary with data volume, retention, and the selected time range.

2. Normalize field names with aliases

Source-specific add-ons may expose the same concept under different field names. A field alias can make common fields easier to use consistently in searches. In the FortiGate example, the incoming source and destination fields are srcip and dstip; the aliases map them to src and dest.

Incoming fieldAlias
srcipsrc
dstipdest

In Splunk Web, open Settings → Fields → Field Aliases → New, then scope the alias to the relevant sourcetype and app. The example object is named fortigate_cim_alias and applies to fortigate_traffic. The configuration screenshot shows Overwrite field values selected; review existing destination fields in your own data before choosing that option.

Validate that the aliases are available at search time:

index=network sourcetype=fortigate_traffic earliest=-24h
| table _time, src, dest, action, protocol
| head 10

This example normalizes two FortiGate fields. A field alias alone does not establish full CIM conformance; validate field meaning and the required data-model fields separately for each source.

3. Enrich events with an asset lookup

A lookup can add stable context such as a hostname, asset role, or priority to events. Build an inventory CSV with a key that matches a field in the event. The example file uses ip, hostname, asset_role, and priority:

ip,hostname,asset_role,priority
192.0.2.10,Splunk-Backend,SIEM,Critical
192.0.2.90,AD-Server,Domain Controller,Critical
192.0.2.35,Win-Endpoint,Workstation,Medium
192.0.2.36,Kali-SOC,Offensive/Test,Low
192.0.2.31,FortiGate-FW,Perimeter Firewall,Critical

The addresses in this public example use the documentation-only 192.0.2.0/24 range. Replace them with the correct addresses for your own inventory; these example addresses are not live asset addresses.

Upload the CSV through Settings → Lookups → Lookup table files, then create a file-based lookup definition. The example definition is asset_inventory, backed by lab_assets.csv. Set its sharing and permissions so intended users and apps can run the lookup.

Match the event source IP to the CSV's ip column and return the desired context:

index=network sourcetype=fortigate_traffic earliest=-24h
| lookup asset_inventory ip AS srcip OUTPUT hostname, asset_role, priority
| table _time, src, srcip, dest, hostname, asset_role, priority, action
| head 10

Keep the inventory current and verify that the lookup key matches the event field exactly. A successful lookup configuration does not guarantee every future event will match; new, missing, or changed asset addresses may have no inventory row.

4. Reuse common searches with macros

Search macros centralize repeated base filters so searches can share a consistent source definition. Create them under Settings → Advanced Search → Search macros. These example definitions use the source values shown above:

MacroDefinitionUse
sysmon_dataindex=wineventlog sourcetype=XmlWinEventLogWindows Sysmon searches
firewall_trafficindex=network sourcetype=fortigate_trafficFortiGate traffic searches

Macro definitions contain the base search. Call a macro with backticks, then add the analysis commands needed for the task:

`sysmon_data`
| stats count by EventCode
| head 10

The screenshot below validates the Sysmon macro by grouping its events by EventCode:

`sysmon_data`
| stats count by EventCode
| head 10

Macro names and definitions are examples. Keep them focused, document what each expands to, and test changes before relying on them in saved searches or dashboards.

5. Classify events with event types and tags

Event types name reusable searches, while tags label the resulting event categories. Define each event type in Settings → Event types → New Event Type, then assign tags that describe the category. The examples shown here are:

Event typeSearch stringTags
Network_Trafficindex=network sourcetype=fortigate_trafficnetwork, communicate
Windows_Authenticationsourcetype=XmlWinEventLog EventCode=4624authentication

Event ID 4624 represents a successful Windows logon, so the Windows_Authentication name and authentication tag match its purpose. Adjust the event type search to your own sourcetype and extracted event-code field.

Validate the authentication event type and the network category with searches such as:

eventtype=Windows_Authentication
| stats count by EventCode
eventtype=Network_Traffic | stats count by action

The screenshot result is a point-in-time view. Counts will change as new events arrive and as the selected time range changes.

6. Validate and maintain the knowledge layer

AreaValidation
Field aliasesConfirm expected source and destination fields appear in search results.
LookupCheck that known asset addresses return the expected hostname, role, and priority.
MacrosConfirm each macro expands to the intended index and sourcetype filter.
Event types and tagsVerify event types return the correct events and tags are attached to the intended categories.

Keep the example values aligned with your deployed add-ons and data. Recheck the sourcetype and field names when inputs or parsing change, review lookup permissions and freshness, and test shared searches after updating a knowledge object.

These objects make searches easier to reuse and interpret; they do not replace validating field semantics, access controls, data quality, or complete CIM coverage for each source.
