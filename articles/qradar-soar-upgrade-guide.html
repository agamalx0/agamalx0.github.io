IBM QRadar SOAR upgrade guide:
prepare, execute & validate

A version-aware procedure for planning an on-premises QRadar SOAR Virtual Appliance upgrade: verify the supported path, prepare backups and maintenance, run the documented installer, monitor the database update, and validate the platform before returning it to service.

Important: this is a Virtual Appliance runbook for on-premises deployments.

IBM's upgrade process differs by deployment model. IBM Security QRadar SOAR on Cloud is updated automatically. If you use a standalone software installation, an App Host, or Disaster Recovery (DR), use the matching official procedure and its required sequence. The conversation that motivated this article covered upgrade planning but did not confirm that an upgrade was executed successfully.

Scope and deployment type

The goal of a SOAR upgrade is to move the platform to a supported release while preserving incident data, playbooks, users, integrations, and service availability. The exact process depends on the current version, target version, deployment type, DR configuration, and whether an App Host is present.

This article uses IBM's current QRadar SOAR 51.0.0 documentation for the Virtual Appliance installer flow. Older SOAR releases may use a different process or older documentation; do not apply the 51.x commands to a different version without checking that version's own instructions.

1. Before you start

  • Identify whether the deployment is the SOAR Virtual Appliance, standalone software, or cloud. Confirm the current platform version and the exact target version.
  • Read the target release notes, upgrade notes, supported upgrade path, and known issues.
  • Apply the latest applicable operating-system and SOAR virtual-appliance security updates that IBM requires before upgrading.
  • Check the current IBM prerequisites for the target release, including required service accounts/groups such as res-email, res-messaging, and res-keystore where specified by the upgrade notes.
  • Arrange an approved maintenance window, user notification, operational owner, recovery owner, and a documented rollback/recovery plan.
  • Check available disk space and system health. The upgrade creates database and search-data backups/snapshots and therefore requires additional space.
  • If an App Host is deployed, review its separate upgrade requirements. If Disaster Recovery is configured, follow IBM's instructions to disable and re-enable DR around the upgrade.
Keep secrets out of the runbook.

Never include API keys, database credentials, encryption secrets, or private certificates in logs shared for troubleshooting. Store backups securely and verify who can access them.

2. Confirm the supported upgrade path

QRadar SOAR 51 uses the IBM VRMF versioning scheme. In this scheme, the third numeric component (Modification) represents a major upgrade step. IBM instructs administrators to move through supported Modification levels sequentially rather than jumping directly to an arbitrary later major level.

  • Example: a supported path may require moving from 50.x to 51.0.0.0 first.
  • Example: a path from 51.0.4.x to 51.0.7.2 requires the intervening major Modification levels—51.0.5.x, then 51.0.6.x, then 51.0.7.x—using the specific installers and fix levels specified by IBM.
  • Within each major level, prefer the latest point release IBM recommends for that upgrade path.

These are examples from IBM's 51.0.0 documentation, not a declaration that any particular source version in your environment is eligible. Confirm the complete path and actual package names in the live IBM release notes before proceeding.

3. Backup and change planning

IBM's documented Virtual Appliance upgrade process automatically backs up the full database. Do not interpret that as a substitute for your organization’s broader recovery plan. Before the maintenance window, verify the backup strategy, available disk space, recovery procedure, and the appropriate off-appliance or platform-level protection available for your deployment.

  • Record the source version, target version, installer file name, installation sequence, start time, and the person responsible for recovery.
  • Confirm there is enough free disk space for the database backup and OpenSearch snapshot. The first snapshot can take longer because it may need to create the initial baseline.
  • For DR deployments, disable DR before upgrading the SOAR Platform, upgrade each appliance as documented, upgrade the DR component to the matching version, and re-enable/synchronize DR as IBM specifies.
  • Keep the relevant release notes, support details, and validation checklist accessible during the change.

4. Obtain the installer

  1. Download the appropriate upgrade package from IBM Fix Central, following the package choice and prerequisites given by your target release.
  2. For the documented SOAR Virtual Appliance flow in 51.0.0 documentation, the installer is named in the form soar-<version>.run. Transfer the exact installer to the appliance using your approved secure file-transfer process.
  3. Verify the downloaded file against IBM's published instructions and checksums, where supplied. Do not execute an unverified installer.

The generic filename shown here is a placeholder, not a downloadable package name. Replace it with the exact versioned filename obtained from IBM.

5. Run the upgrade

SSH to the SOAR Virtual Appliance with an authorized administrative account, change to the directory where the verified installer is stored if necessary, and run IBM's documented command using the actual installer version:

sudo bash soar-<version>.run

For example, the placeholder <version> is replaced with the version specified by the installer filename. When prompted, review the installer information and confirm that you want to continue. Do not copy the placeholder literally or substitute a command from an unrelated QRadar SIEM procedure.

Do not use a guessed upgrade command.

The earlier generic advice in this conversation mentioned resutil upgrade, resutil version, and resutil status. Those commands were not established by the cited Virtual Appliance upgrade guide and should not be treated as the authoritative SOAR 51.x upgrade procedure. Use the exact commands documented for your deployment and release.

6. Monitor progress

If the database upgrade takes longer than expected, IBM documents checking the timestamped database update log:

sudo tail -f /usr/share/co3/logs/update_database_x.log

Replace x with the timestamp/identifier of the actual update_database_* log on the system. The Virtual Appliance upgrade also creates an OpenSearch snapshot. IBM identifies snapshot logs in this pattern:

/usr/share/co3/logs/create_es_snapshot_before-upgrade-<version>.log

For a V51 transition from PostgreSQL 12 to PostgreSQL 14, IBM notes that the platform performs a PostgreSQL migration and additional backup work; this can make the upgrade take longer than usual. Check the version-specific logs and allow the documented process to finish rather than interrupting it because it appears idle.

7. Post-upgrade checks

The conversation did not include a completed upgrade or successful validation output. After your actual upgrade finishes, record the evidence for each relevant check and compare it with the pre-upgrade baseline:

  • Confirm the installed platform version in the supported version display or command for that release.
  • Verify the web interface and authentication, incident lists/details, search, playbooks, and dashboards.
  • Confirm expected database/search functionality. For releases that perform a full search reindex, IBM notes that some search functionality may be unavailable until reindexing completes.
  • Check application integrations and the App Host if deployed. Run a controlled integration test rather than assuming that a successful platform login proves all apps work.
  • For HA/DR, verify the documented appliance versions, synchronization, and recovery state before closing the change.
  • Record alerts, logs, skipped or failed steps, and the final version. Keep pre-upgrade recovery material according to your retention policy.

Known issues & troubleshooting

Installer reports “Post-installation setup has failed”

IBM documents a release-specific rollback path for this failure. First capture the exact error and relevant logs, then use the procedure for your source/target release and approved recovery plan. IBM's 51.0.0 guide says to list package transaction history:

sudo yum history

Then use the matching pre-upgrade restore-point directory and the backup package ID shown by that history (the angle-bracket values are placeholders):

sudo /crypt/resRollbackServerUpgrade /crypt/db_restore_points/before-upgrade-<version>-<date> <backup_package_ID>

Do not copy the placeholders literally. If the rollback utility cannot find the backup set, follow IBM's documented pgBackRest restore-point procedure before rolling back the SOAR application. This is a controlled recovery procedure, not a routine validation command; do not improvise or run it without confirming the correct restore point and package ID.

Upgrade path rejected or installer cannot proceed

Do not force a direct upgrade. Confirm the installed source version, installer file name, package notes, and each required intermediate Modification level. Download the packages IBM lists for the path from Fix Central.

Upgrade appears to take a long time

Inspect the timestamped database-update log and, where applicable, the OpenSearch snapshot log shown above. Snapshot creation and PostgreSQL migration/backup work can take additional time, especially during a first snapshot or a V51 database migration. Do not kill the installer or reboot the appliance without IBM-directed recovery instructions.

Insufficient disk space

The upgrade requires temporary space for backup and search snapshot data. Check free space before the window and review IBM's documented cleanup process for your release. Do not remove database or OpenSearch files manually as a shortcut.

Disaster Recovery or App Host present

Use their own upgrade instructions and required sequencing. IBM says DR must be disabled before upgrading SOAR and that both the platform and DR system must end up on the same version. App Host software has a separate procedure.

App or integration fails after upgrade

First confirm the core platform is healthy, then inspect the relevant app/integration logs and revalidate its configuration and compatibility. A 403 Forbidden or an app-specific API error is not, by itself, evidence that the platform upgrade failed. Check API-key ownership, role permissions, endpoint access, certificate handling, and the relevant app's documentation. The earlier log in this conversation showed a 403 during an application connection check, but no confirmed fix was recorded.

Key lessons

  • Use the upgrade guide for the precise deployment type; QRadar SIEM and QRadar SOAR are different products with different upgrade processes.
  • Do not assume any direct version jump is supported. For SOAR 51.x, follow each required Modification upgrade step.
  • Plan for database backups and OpenSearch snapshots, and include their disk requirements and time in the change window.
  • Treat App Host and DR as separate but coordinated workstreams.
  • Document validation evidence. This article explains the process; it does not claim an upgrade was executed or validated in this conversation.
